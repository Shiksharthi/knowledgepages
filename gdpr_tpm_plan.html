Technical Program Manager — Action Plan

GDPR Compliance & Data Quality
Remediation Plan

A plain-language, step-by-step guide to finding PII data that's out of compliance, cleaning inconsistent or duplicate data, and building controls so the problem doesn't come back.

Scope: Structured data only Stores: Databases · Cache · Data Lake Risk: PII · GDPR exposure Problems: Inconsistent format · Duplicates · Compliance gaps Phases: 7 · ~6–9 months total
⚠️
Before you start: Involve your Legal/Privacy team and Data Protection Officer (DPO) from Day 1. GDPR violations can result in fines of up to €20 million or 4% of global annual turnover — whichever is higher. Document everything you do as proof of compliance effort.

1
Discover & Map — Know What You Have
You cannot fix what you cannot see. Build a complete map of all your data before doing anything else.
Weeks 1–4
Think of this like a house inspection before renovation. Before you touch anything, you walk through every room and write down what's there. Here, your "rooms" are every database, cache cluster, and data lake partition that your company owns.
1.1
List every single data store
Create a master spreadsheet (your "Data Store Register") listing every place data lives — every database instance, every cache cluster (Redis, Memcached), every data lake bucket/folder. Include the environment (production, staging, dev) and the team that owns it.
WhoTPM + Engineering leads from each team + Infrastructure team
HowSend a questionnaire to each team lead. Cross-check with cloud infrastructure dashboards (AWS Console, GCP Resource Manager, Azure Portal) to find stores that teams forgot to mention.
ToolsAWS Config · Azure Resource Graph · GCP Asset Inventory · Confluence/Notion for tracking
Risk if skippedYou'll miss "shadow" databases that teams set up informally — these are often the most non-compliant because no one is watching them.
1.2
Catalog every table and column with PII
For each data store, list all tables (or collections/schemas). For every table, identify which columns contain PII — names, email addresses, phone numbers, IPs, dates of birth, social security numbers, credit card data, home addresses, device IDs, etc.
HowStart with automated scanning tools (they flag obvious PII fields by column name and content patterns). Then have a human review to catch things the tool missed — e.g. a column called "notes" that stores free-text with phone numbers buried inside.
ToolsAWS Macie · Google Cloud DLP (Data Loss Prevention) · Microsoft Purview · Collibra · Informatica · Alation
GDPR linkGDPR Article 30 requires a Record of Processing Activities (RoPA) — this step is how you build it.
Name / Full NameEmailPhoneDOBSSN / NINIP AddressLocation / AddressDevice IDCookie IDFinancial DataHealth DataBiometric
1.3
Assign a Data Owner to every data store
Every database, cache, and data lake partition must have a named person (Data Owner) who is accountable for its compliance. Without a named owner, nothing gets fixed — responsibility evaporates into "someone else's problem."
WhoUsually the Engineering Manager or Product Manager of the team that built/uses the system.
GDPR linkGDPR requires identifying who is the Data Controller (your company) and any Data Processors (3rd-party services you share data with).
TPM TipAdd a "Data Owner" column to your master spreadsheet. Send a weekly reminder to anyone with empty owner fields until all stores are assigned. No exceptions.
1.4
Map data flows — where does data come from and go?
Draw a map (a Data Flow Diagram) showing how user data enters your systems and where it travels. For example: "User signs up on the website → stored in User DB → copied to Data Lake every night → exported to our email marketing vendor." Every arrow on this map is a risk point.
HowInterview engineering teams and review ETL/pipeline code. Most data platforms have lineage features built in.
Toolsdbt lineage graph · Apache Atlas · Collibra Lineage · DataHub · Amundsen
GDPR linkAny transfer of PII to a 3rd party (vendors, analytics tools, ad platforms) may require a Data Processing Agreement (DPA) and may restrict transfer outside the EU.

2
Profile & Assess — Understand the Mess
Run analysis on the actual data to find format inconsistencies, duplicates, and quality problems.
Weeks 3–7
Think of this like a blood test. You now know what organs exist (your data stores). Now you run tests on each one to find out what's wrong. This phase is about measuring — not fixing yet.
2.1
Run Data Profiling on every PII table
Data profiling is automated analysis that checks the health of each column. It answers: "What does the data in this column actually look like?" For each column, it tells you: how many nulls/blanks, what values appear, are the formats consistent, are there outliers or garbage values.
What to checkNull rate (% of empty values), Uniqueness (how many distinct values), Format patterns (e.g. are all phone numbers in the same format?), Value ranges (are DOB years reasonable?), Data types (is a "phone" column sometimes storing letters?)
ToolsGreat Expectations · Apache Griffin · Deequ (AWS) · Talend Data Quality · SQL queries with GROUP BY / COUNT / DISTINCT
Example finding: "email column has 23% nulls" "phone stored in 6 different formats" "DOB has future dates — impossible"
2.2
Find duplicate and redundant records
The same person's data might exist multiple times — different spellings of their name, slight variations in email, or the same record copied to 5 different tables. Duplicates inflate storage costs, make GDPR "right to erasure" requests a nightmare, and create inconsistency.
HowExact duplicates: Same values in key fields (email + DOB = same person). Easy to detect with SQL. Fuzzy duplicates: "John Smith" vs "Jon Smith" — require fuzzy matching algorithms. Cross-store duplicates: Same user in the Users DB and the Analytics DB — check using email or user ID as a join key.
ToolsSQL DISTINCT / GROUP BY queries · Python (pandas dedup) · Dedupe.io · Informatica MDM · Talend · dbt tests
GDPR linkIf a user submits a "Right to Erasure" request (right to be forgotten), you must delete them from ALL stores. Duplicates you don't know about = compliance violation you can't see.
2.3
Identify format & type inconsistencies
The same field stored in 5 different ways across your systems. This happens because different teams built different services at different times without agreeing on standards. Common examples are shown below.
Examples Date of Birth: "15/04/1990" vs "1990-04-15" vs "April 15, 1990" vs timestamp
Phone: "+1-555-123-4567" vs "5551234567" vs "(555) 123 4567"
Name: "JOHN SMITH" vs "john smith" vs "Smith, John"
Country: "United States" vs "US" vs "USA" vs "840" (ISO numeric code)
How to findRun REGEX pattern analysis on each PII column. Count how many distinct patterns exist. More than 2–3 patterns for the same field = inconsistency problem.
2.4
Check data retention — how old is this data?
GDPR says you can only keep personal data for as long as you actually need it (the "storage limitation principle"). Run a query to find how old your data is. Records from 7+ years ago for users who never returned are likely in violation — you have no legal reason to still hold them.
HowQuery the created_at / updated_at timestamp column in each table. Group by year. Compare against your privacy policy's stated retention period.
GDPR linkArticle 5(1)(e) — "Storage limitation": data must not be kept longer than necessary. If you told users "we keep your data for 2 years" in your privacy policy, data older than 2 years is a violation.
WarningCache layers (Redis etc.) often store PII with no TTL set — data stays forever unless someone explicitly deletes it. Check TTL settings on every cache key that might hold PII.

3
GDPR Gap Analysis — Find the Legal Violations
Map every piece of PII data against GDPR requirements and identify exactly where you're non-compliant.
Weeks 5–8
Think of this like comparing your building against fire safety codes. You have a map of your building (Phase 1) and you know what's broken (Phase 2). Now you check each finding against the law to classify it: "legal violation," "operational risk," or "just messy but not illegal."
3.1
Check: Do you have a legal basis for each type of PII?
GDPR requires a "lawful basis" for processing every type of personal data. For each PII field you found, you need to answer: WHY are we storing this? The six valid reasons under GDPR are listed below. If you can't justify a field with one of these — delete it.
6 Lawful Bases 1. Consent — user explicitly agreed (ticked a box, signed up)
2. Contract — needed to deliver the service they paid for
3. Legal obligation — law requires you to keep it (e.g. tax records)
4. Vital interests — needed to protect someone's life
5. Public task — government functions
6. Legitimate interests — your business need outweighs privacy risk (use carefully)
ExampleYou collect users' date of birth for age verification. Lawful basis = Contract. Fine. But if you're also storing their browsing history for no documented reason — that's a gap.
3.2
Check: Can users exercise their rights?
GDPR gives users 8 rights. You need to be technically able to honor ALL of them within 30 days. For each right, test whether you can actually do it. Most companies discover they can't — especially for data scattered across many stores.
8 User Rights to Test 1. Right to access — "Show me all data you have about me" → Can you export it from ALL stores in 30 days?
2. Right to rectification — "Fix my wrong data" → If they update their email, does it update everywhere?
3. Right to erasure — "Delete me" → Can you find and delete from ALL stores including cache & data lake?
4. Right to restrict processing — "Don't use my data for X" → Can you flag and stop specific processing?
5. Right to data portability — "Give me my data in a usable format"
6. Right to object — "Stop processing my data for marketing"
7. Rights related to automated decision making — "Explain any automated decisions about me"
8. Right to withdraw consent — If consent was the basis, can they withdraw it?
3.3
Check: Is PII encrypted and access-controlled?
PII in a plain-text column that any analyst can query is a major risk. GDPR requires you to implement "appropriate technical measures" to protect personal data. Run an access audit to find out who can see PII right now.
What to check Is PII encrypted at rest (on disk) and in transit (network)?
Who has SELECT access to PII tables? (Principle of least privilege — only those who need it should have it)
Are production PII tables visible to developers running local queries? (they shouldn't be — use masked/synthetic data for dev)
Are database credentials shared or individual? (shared = can't audit who did what)
ToolsDatabase audit logs · IAM role review · Column-level encryption tools · Dynamic data masking (SQL Server, Oracle, Snowflake)
3.4
Check: Are 3rd-party data transfers legal?
Every time PII leaves your systems and goes to a vendor — your email platform, analytics tool, CRM, ad network — that's a data transfer. Each one needs a legal contract (Data Processing Agreement). If PII goes outside the EU/UK, you need additional protections.
HowReview your Data Flow Diagram from Phase 1. For every external arrow (data leaving your systems), check: Do you have a signed DPA with that vendor? Is the vendor EU-based or using SCCs/Adequacy decisions for US transfers?
GDPR linkChapter V of GDPR governs international data transfers. Sending EU user data to the US or other non-adequate countries without Standard Contractual Clauses (SCCs) = violation.

4
Prioritize & Plan — Decide What to Fix First
You now have a big list of problems. Not everything can be fixed at once. Rank by risk and build a realistic roadmap.
Weeks 7–9
Think of this like hospital triage. You've diagnosed all the patients. Now you decide: who needs emergency surgery now (P0), who needs treatment this week (P1), and who can wait for a scheduled appointment (P2). Fix the life-threatening problems first.
4.1
Score every finding by Risk × Volume × Effort
For each problem found in Phases 2 and 3, assign scores for: how severe is the GDPR risk, how many users are affected, and how hard is it to fix. Multiply these together to get a priority score.
Formula Risk: 3 = regulatory fine likely · 2 = data breach risk · 1 = operational only
Volume: 3 = affects millions of users · 2 = thousands · 1 = hundreds
Effort to fix: 3 = quick win (days) · 2 = medium (weeks) · 1 = complex (months)
Priority Score = Risk × Volume × Effort — fix highest scores first
P0 examplesUnencrypted PII visible to all employees · Data with no legal basis · Inability to honor erasure requests · PII sent to vendor with no DPA signed
4.2
Create a Remediation Roadmap with clear owners
Turn your prioritized list into a proper project plan. Each item needs: a clear description of what needs to change, a named owner (engineer or team), a target date, and measurable success criteria. Without these four things, nothing gets done.
Structure Month 1 (Emergency): P0 issues — legal violations that could result in fines right now
Months 2–3 (High Priority): P1 issues — major data quality problems, access control gaps
Months 4–6 (Systematic): P2 issues — format standardization, deduplication, retention cleanup
Ongoing: P3 — nice-to-have improvements and technical debt
ToolsJira · Linear · Asana · Notion — track as epics/tickets with due dates
4.3
Get executive sign-off and budget
Present the findings to leadership in business language, not technical language. Show them: "We found X issues. The GDPR fine risk is €Y. It will cost Z to fix. Here's the plan." Get formal approval so you have budget, headcount, and executive backing to override teams that push back.
TPM TipCreate a one-page executive summary with a traffic light (Red/Amber/Green) status for each data store. Executives make decisions fast when they can see the picture at a glance. Save the 50-page technical report as an appendix.
AttendeesCTO or VP Engineering · Legal / DPO · CISO (security) · Product leadership · You (TPM)

Risk-scored issue register
Remediation Roadmap (Gantt/timeline)
Executive summary deck
Approved budget & headcount
Owner assignments per issue
5
Clean & Fix — Do the Actual Work
Execute the remediation plan. Fix data quality issues, remove non-compliant data, and harden access controls.
Months 2–5
Think of this like the renovation itself. Plans are approved, budget is secured. Now the work gets done — in the right order, carefully, with testing at each step. Never run bulk data changes on production without testing on a copy first.
5.1
Delete data with no legal basis & expired retention
This is the most urgent GDPR fix. Data you have no right to hold must be deleted. Data older than your stated retention period must be deleted. This is not optional. Always take a backup before deleting, archive to secure cold storage if legally required (e.g. tax records), then delete.
Process1. Write a deletion script → 2. Test on a copy of data → 3. Have legal approve the deletion list → 4. Run with a transaction (so you can roll back if something breaks) → 5. Log every deletion with a timestamp and who authorized it
WarningFor the data lake: deletion is harder (you can't just DELETE a row in Parquet/ORC files). You'll need to rewrite partitions. Plan extra time for data lake cleanup — it's the most technically complex part.
Cache (Redis etc.)Set a TTL (Time To Live) on every cache key that holds PII. A TTL of 24 hours is reasonable for most session data. Keys with no TTL = data lives forever = violation.
5.2
Standardize PII field formats
Normalize inconsistent fields to a single agreed standard across all stores. This makes future analysis reliable and GDPR requests (like "find all data for this person") actually workable.
Standards to adopt Phone numbers: E.164 format (+15551234567) — international standard
Dates: ISO 8601 (YYYY-MM-DD) — unambiguous globally
Names: Store First Name and Last Name in separate columns. Store the original if needed.
Emails: Always lowercase. Validate format with REGEX on write.
Country: ISO 3166-1 alpha-2 codes (US, GB, DE, FR)
TPM TipWrite the standard down in a shared "Data Standards Document" that all engineers must follow. This is your reference for Phase 6 (governance). If it's not written down, teams will go back to their own formats within 3 months.
5.3
Deduplicate records and merge correctly
Remove duplicate records — but do it carefully. You need to decide which copy is the "golden record" (the truth). You can't just delete one randomly — you need business rules. For example: "keep the most recently updated record" or "prefer the record with the most complete fields."
Steps1. Identify duplicates (from Phase 2 output) → 2. Define survivorship rules ("which copy wins?") with business stakeholders → 3. Merge or delete duplicates → 4. Update any foreign keys pointing to deleted records → 5. Verify downstream systems still work
RiskDeduplication can break downstream systems that have foreign key references to the deleted records. Always check what depends on the records you're merging before deleting.
5.4
Restrict access to PII — Least Privilege
Remove broad access to PII tables. Only people whose job requires seeing raw PII should have access. Everyone else should see masked/anonymized versions. This is also a security win — a stolen analyst account can't access all your user data.
Actions Revoke broad SELECT access to PII tables for all users → Create role-based access groups (Customer Support, Data Science, Engineering) → Each group gets only the columns they need → Implement dynamic data masking (email shows as "j***@g***.com" for unauthorized users) → All access changes are audit-logged
ToolsPostgreSQL RLS (Row-Level Security) · Snowflake Column Masking Policies · BigQuery column-level security · AWS Lake Formation for data lake access control
5.5
Pseudonymize or anonymize PII where possible
If a team only needs to analyze patterns (not identify specific people), give them anonymized data instead of real PII. This reduces your GDPR exposure — anonymized data is not covered by GDPR at all. Pseudonymization replaces real identifiers with a code (still reversible by authorized users). Anonymization is permanent (irreversible).
Use cases Analytics team studying purchase patterns → give them anonymized user IDs, not real emails
ML training → use synthetic data generated from real patterns, not actual PII
Dev/test environments → never use real PII. Use masked or synthetic copies only.
ToolsGoogle Cloud DLP tokenization · AWS Glue · Databricks Delta · Faker/Mimesis (Python synthetic data) · ARX (anonymization tool)

6
Govern & Control — Stop the Problem Coming Back
Build automated guardrails so new data is captured correctly from day one and compliance is maintained without manual effort.
Months 4–6
Think of this like installing a new building code for the future. You've cleaned the mess. Now you put in smoke detectors, sprinklers, and fire exits so the next fire is caught early and can't spread. Without governance, teams will recreate the same mess within 12 months.
6.1
Enforce data validation at ingestion (write time)
The cheapest time to fix bad data is before it enters your system. Add validation rules at the point where data is written — API endpoints, ETL pipelines, database insert triggers. Reject bad formats before they get stored.
Examples API rejects an email that doesn't match REGEX pattern before saving → ETL pipeline fails and alerts if a DOB is in the future → Database CHECK constraint prevents phone numbers shorter than 7 digits → Schema validation (JSON Schema / Avro / Protobuf) enforces field types in data pipelines
ToolsGreat Expectations · dbt tests · Apache Avro/Protobuf schema registry · SQL CHECK constraints · API-level validation (Pydantic, Joi, Zod)
6.2
Implement automated data quality monitoring
Set up dashboards and alerts that continuously check data quality. If the null rate for the email column suddenly jumps from 2% to 40% — you get alerted immediately, not 3 months later when a customer complains.
Metrics to monitor Null rate per PII column · Duplicate rate per table · Format conformity % · Record count vs. expected range · Data freshness (is the pipeline running on time?) · Retention age (flag records approaching deletion date)
ToolsGreat Expectations + Slack alerts · Monte Carlo · Bigeye · dbt + elementary · Grafana dashboards on data quality metrics
6.3
Automate data retention deletion
Don't rely on humans to remember to delete old data. Set up scheduled jobs that automatically delete or anonymize records that have exceeded the retention period. This makes GDPR compliance continuous, not a one-time cleanup.
HowFor each table with PII, create a scheduled job (cron/Cloud Scheduler) that runs monthly. It deletes or anonymizes records where (current_date - created_at) exceeds your retention policy. Log every deletion. Alert on failures.
Data Lake tipUse partition-based retention: store data in partitions by year/month (e.g. /data/users/2021/). Dropping a whole partition (DELETE partition) is far faster than row-by-row deletion in large-scale data lakes.
6.4
Build a self-service GDPR request handler
When a user emails your support team saying "Delete my data" — you currently have to do it manually. That doesn't scale and causes 30-day deadline misses. Build or buy a system that routes GDPR requests to all relevant data stores automatically.
What it doesCustomer Support logs the request → System identifies all stores containing that user's data (using user ID or email as a lookup key) → Deletion/export job runs across all stores → Automated confirmation is sent to the user → Request is logged with timestamp for audit purposes
ToolsOneTrust · Transcend.io · Ethyca · Custom-built workflow using your existing job scheduler + a data subject index
Phase 6 Deliverables

Data quality monitoring dashboard

7
Prove & Monitor — Show You're Compliant, Stay Compliant
Create the documentation and ongoing processes that prove compliance to regulators, auditors, and customers.
Ongoing from Month 3
Think of this like maintaining a fire safety logbook. The inspection is passed, the building is safe — but you need to keep dated records that prove it, re-inspect regularly, and update the logbook every time something changes. Regulators don't just want you to be compliant — they want proof.
7.1
Finalize and maintain the Record of Processing Activities (RoPA)
The RoPA is your official GDPR register — a document that lists every type of personal data you process, why you process it, who has access, how long you keep it, and where it goes. GDPR Article 30 makes this legally mandatory for most organizations. If a regulator asks for it, you must produce it.
What it containsName of processing activity · Purpose & lawful basis · Categories of PII · Which systems hold it · Who has access · Retention period · 3rd-party recipients · Security measures
TPM TipReview and update the RoPA every 6 months and whenever a new feature is built that processes PII. Assign this review as a recurring calendar event for each Data Owner.
7.2
Run quarterly internal audits
Every quarter, run a lightweight audit: re-run the data quality checks from Phase 2, verify retention jobs ran successfully, check that no new stores appeared without being registered, review access logs for anomalies, and confirm all GDPR requests were handled within 30 days.
Who runs itTPM coordinates. Data Owners complete their section. Legal/DPO reviews the results. Results presented to CISO and CTO quarterly.
Checklist itemsNew data stores since last audit → PII in unexpected columns (re-run DLP scan) → Retention job logs (did they run? did they fail?) → Access control changes (new users with PII access?) → GDPR request log (all answered within 30 days?)
7.3
Build a "Privacy by Design" checklist for new features
The root cause of your data mess is that teams built features quickly without thinking about data compliance. Fix this at the source: add a mandatory data privacy review to every new feature that touches or creates PII. Make it part of the design/PRD process, not an afterthought.
Checklist questions Does this feature create or process any PII? If yes →
What is the lawful basis? →
Have you registered it in the RoPA? →
Where will this data be stored, and for how long? →
Who will have access? →
Has Legal/DPO approved? →
Is a DPIA needed (high-risk processing)?
Where to embed itAdd as a required section in your PRD (Product Requirements Document) template. Add to engineering's Definition of Done checklist. No PII-touching feature ships without it being answered.
7.4
Train all teams on data handling basics
Technical fixes only work if people understand why they matter. Run a short annual training for engineers, data analysts, product managers, and customer support. Focus on: what counts as PII, what they're allowed to do with it, and what to do if they accidentally see or leak it.
Format30-minute online module + quiz (mandatory annual) · "Data Incident Response" card (what to do if you accidentally export PII to the wrong place — you have 72 hours to report a breach to the regulator under GDPR)
GDPR linkArticle 33 — you must report data breaches to your supervisory authority within 72 hours of becoming aware. Train your team so they recognize and report incidents fast — don't let 72 hours pass because someone wasn't sure if it was "a real breach."

Golden Rules for the TPM Running This Program

01Always involve Legal / DPO from Day 1. Technical fixes without legal guidance can create new risks. Every deletion needs legal sign-off.
02Never fix data without a backup and a rollback plan. One bad script on a production database can corrupt millions of records permanently.
03Document everything, even when it slows you down. Regulators don't just want compliance — they want proof. An undocumented deletion is legally invisible.
04Name an owner for every data store. Ownerless data is everyone's problem and no one's priority. Problems only get fixed when one named person is accountable.
05Phases 1–4 can run in parallel where possible. Discovery (Phase 1) and profiling (Phase 2) overlap. GDPR gap analysis (Phase 3) starts before Phase 2 finishes. Don't run purely sequentially — it takes too long.
06GDPR compliance is a continuous program, not a one-time project. The real risk isn't the initial cleanup — it's drifting back into non-compliance 6 months later. Phase 7 never ends.
This plan covers GDPR as it applies to EU/UK structured data. Consult your DPO for jurisdiction-specific rules (CCPA for California, PDPA for India, LGPD for Brazil, etc.).
