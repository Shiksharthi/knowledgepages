04 · Services

Core Microservices — Roles & Technology

Each service owns its domain, its own data store, and its own scaling strategy.

Catalog Service

MongoDB + Redis

Product data, images, specs, pricing.

↑ Read replicas + Redis cache (95% hit rate)

Search Service

Elasticsearch + Kafka

Full-text search, autocomplete, ML ranking.

↑ 5-node cluster, index sharding by category

Cart Service

Redis + DynamoDB

Cross-device cart state, 90-day TTL.

↑ Write-through cache, sticky sessions

Order Service

PostgreSQL + Kafka

Order lifecycle, ACID transactions.

↑ Saga pattern, shard by user_id mod 10

Payment Service

Stripe + Adyen (backup)

Tokenization, auth/capture, fraud ML.

↑ Multi-gateway failover, circuit breaker

Inventory Service

Redis + Kafka CDC

Real-time stock across warehouses.

↑ Distributed locks, Redis DECR atomic

User Service

PostgreSQL + JWT/Redis

Auth, profiles, address book.

↑ JWT caching 24h, replicas for reads

Notification Service

SendGrid + Twilio + FCM

Email, SMS, push, in-app alerts.

↑ Kafka priority queue, K8s autoscaling

08 · Storage

Database Architecture — Three-Layer Storage Strategy

Read/write ratio: 95% reads / 5% writes — optimize with read replicas, CDN, and multi-level caching.

PostgreSQL

Orders · Users · Payments
ACID transactions — financial accuracy required.
orders(id, user_id, status,
       total, created_at)
order_items(id, order_id,
       product_id, qty, price)
payments(id, order_id, amount,
       status, gateway_txn_id)
Shard by user_id mod 10 · Primary + 2 replicas · PgBouncer pooling · Multi-AZ, auto-failover <30s, 1M+ QPS (TiDB in Flipkart)

MongoDB

Product Catalog · Sessions
Flexible schema — products have varying attributes.
{ _id: "SKU-123", title, brand,
  price, images[],
  specifications: { color,
    wireless, battery },
  inventory: { wh1: 347,
    total: 476 } }
Replica sets (1 primary + 2 secondary) · Partition by category · Atlas · 80% reads on top 5% of products — cache reduces DB load 20×

Elasticsearch

Product Search Index
Sub-50ms full-text search across billions of products.
{ product_id, title,
  description, brand,
  category[], price, rating,
  review_count, in_stock,
  popularity_score }
5-node cluster (3 data + 2 master) · Shard by category · Kafka CDC · Near-real-time indexing <30s delay · Fallback: PostgreSQL full-text if ES down

⚡ Redis cache layer sits in front of all three: TTL 1–60 min for hot data, 0.12ms p50 latency.

09 · Scaling

Scalability Strategies — 5 Key Pillars

1 · Horizontal Scaling

Add more servers; Kubernetes HPA auto-scales pods on CPU/RPS.

🏢 Flipkart: 2K → 10K+ API pods during Big Billion Days
K8s HPA (scale at CPU > 70%) · AWS Auto Scaling Groups · 10× capacity

2 · Multi-Layer Caching

Browser → CDN → API Gateway → Redis → DB (each layer 10–100× faster).

🏢 Amazon: 90% of traffic served from CloudFront (300+ PoPs)
Redis 0.12ms p50 · CDN cache TTL 24h images · 95%+ hit rate

3 · Database Sharding

Split data across DBs: hash by user_id, range by time, geo by region.

🏢 Instagram: user data sharded across 100+ PostgreSQL DBs
TiDB auto-sharding · Shard = hash(user_id) mod 10 · 1M+ QPS

4 · Async Processing

Kafka queues decouple services; email/push sent after checkout returns.

🏢 Checkout: 1.3s (was 2s) by making email async via Kafka event
Kafka topics per domain · Consumer groups · Dead-letter queues

5 · CDN + Edge Computing

Static assets + dynamic edge logic at 300+ PoPs worldwide.

🏢 Temu: 40% faster load times via CDN edge optimization
CloudFront 600+ PoPs · Cloudflare Workers <50ms global · WebP images

11 · Availability

Fault Tolerance & High Availability

Target: 99.99% uptime = 52 minutes of downtime per year.

ComponentFailure RiskMitigation StrategyRecovery
Load BalancerEntire site down if single LB failsActive-active multi-AZ + DNS failover<60s
Database PrimaryNo writes if primary crashesStreaming replication, auto-failover<30s
Payment GatewayNo orders if Stripe is downMulti-gateway: Stripe → PayPal backup<5s
Search (ES)Search broken for all users3–5 node cluster + SQL LIKE fallbackInstant
Cache (Redis)DB overloaded, slow responsesRedis Cluster + cache-aside (tolerate miss)None needed

Circuit Breaker Pattern

CLOSED (serving traffic) │ ▼ 5 consecutive failures OPEN (fail fast, 60s cooldown) │ ▼ cooldown elapses HALF-OPEN (try one request) │ ├─ success → CLOSED └─ failure → OPEN

Used by: Flipkart ES fallback · Walmart payment gateway · Netflix auth  |  Libraries: Hystrix (Java) · resilience4j · Polly (.NET)

Data Consistency Models

StrongOrders / Payments — slower writes (must sync replicas).
EventualProduct Catalog — stale data for 1–5s is acceptable.
CausalUser Reviews — your own posts are visible immediately.

When to Use This Architecture

✓ Use This Design When…

High Traffic (>100K daily users)
Need horizontal scaling, load balancing, caching
Multi-Vendor (>100 sellers)
Need seller onboarding, inventory management
Global Operations (multi-country)
Need multi-region CDN, localization
Real-Time Inventory (warehouses/stores)
Need event-driven, Kafka CDC, Instacart-style
AI/ML Personalization
Need ML infra, feature stores, A/B testing
99.99% Uptime SLA required
Need multi-AZ, circuit breakers, failover

✕ Avoid This Design When…

Small Business (<10K monthly users)
Over-engineered → use Shopify ($29/mo)
Single Vendor (you own all inventory)
Simpler alternative: WooCommerce / Magento
Low Budget (<$50K/month infra)
Use serverless: Firebase + Stripe + Vercel
B2B with Batch Processing
Enterprise: SAP Commerce, Oracle Commerce
Local/Regional Only (1 city)
Single AWS region + CloudFlare free tier
Content-First with Occasional Sales
WordPress + WooCommerce / Gumroad
14 · Summary

Key Takeaways

Everything you need to design a world-class marketplace.

01

Microservices are standard

90% of new apps. Each service owns its domain: Catalog, Cart, Order, Payment, Inventory, Notification.

02

Cache everything

90%+ of reads. Redis → 0.12ms p50. CDN → 300+ PoPs. Multi-level: Browser → CDN → Redis → DB.

03

Design for failure, not uptime

Circuit breakers, multi-gateway payments, multi-AZ DBs, Saga pattern for distributed transactions.

04

Kafka decouples everything

Async: order confirmed in 1.3s (not 2s). Events flow: inventory, notifications, analytics.

05

Eventual consistency is fine for catalog

Strong consistency for $ (orders/payments). Eventual OK for product descriptions, reviews.

06

Observe → measure → optimize

4 Golden Signals: Latency, Traffic, Errors, Saturation. P0/P1/P2 alert tiers.

Real-world references: Amazon · Walmart · Flipkart (TiDB 1M QPS) · Coupang (Vitamin MQ) · Instacart (80K stores, Kafka) · Temu (C2M, 90 markets)
